# Phase 0.5: Design-System Finalization Brief

Status: **current — next V2 design activity**

This brief turns the accepted V2 references into a usable visual and
interaction-design authority before Local Web Foundation implementation. It is
a bounded handoff and coherence review, not a new product-discovery cycle.

## Purpose And Boundary

The question for Phase 0.5 is:

> Can later implementation extend V2 while preserving its product truth,
> distinctive visual hierarchy, and consequential-state behavior?

Gates 1–7, the product model, the contracts, and the accepted prototypes remain
authoritative. Phase 0.5 may improve a surface system when coherence requires
it, but it does not reopen accepted interaction semantics for visual taste,
copy polish, or implementation convenience.

## Method

1. **Review the accepted system together.** Inspect the Composite, Acquire,
   Run Authority, and Process references as one product at wide desktop,
   compact desktop, and read-only phone widths.
2. **Start from product truth.** For every reusable visual pattern, name the
   operator job, canonical owner, evidence, eligibility, consequence, and
   recovery behavior before defining its presentation.
3. **Use native working objects as the source of identity.** The active run,
   plan/timeline, solve evidence, Process canvas, context rail, and Library
   asset lineage should carry more product character than generic containers or
   decoration.
4. **Audit for genericness through product evidence.** Ask whether an unrelated
   product could replace V2 nouns without materially changing the screen. If
   yes, improve domain evidence, priority contrast, structural specificity, or
   state coverage—not novelty for its own sake.
5. **Validate awkward states, not just ideal screenshots.** Include healthy,
   warning, blocked, recovery, reconnect, stale, permission/read-only,
   destructive, dense-content, compact, and phone states as relevant.
6. **Record and accept explicitly.** Keep selected rules, intentional
   exceptions, rejected alternatives, deferred questions, validation evidence,
   and one next action in current authority. Owner acceptance freezes the guide
   as Phase 1's visual implementation authority.

## Design Thesis To Establish

Phase 0.5 must write two or three falsifiable theses that bind product truth,
interface behavior, and visual character. A thesis fails if it could describe
an unrelated product unchanged.

The expected V2 direction is dense but calm observatory work: current service
truth, the useful decision, and the evidence supporting it outrank decorative
chrome. Familiar interaction conventions remain where safety, accessibility,
or learned behavior matters; product-specific hierarchy comes from the actual
objects and consequences of observatory work.

## Guide Deliverable

The official V2 style and design guide should include:

1. product and design thesis;
2. users, operator jobs, language, and field/environment constraints;
3. information model, canonical ownership, freshness, authority, and state
   semantics relevant to presentation;
4. workspace, navigation, persistent active-run, and responsive model;
5. consequential-action rules: automatic, available, unavailable,
   approval-required, stale, destructive, recovery, save, discard, and
   handoff;
6. native working objects and visual-hierarchy rules;
7. typography, semantic color/status treatment, spacing, surfaces, controls,
   icons, imagery, focus, and motion;
8. tokens, component patterns, state variants, and intentional exceptions;
9. content, accessibility, keyboard, and reduced-motion guidance;
10. representative ordinary and awkward states;
11. accepted reference prototypes and scenarios;
12. rejected alternatives, deferred questions, maintenance, and extension
    rules for later implementation work.

The guide explains why a rule exists. Consistency alone is not a sufficient
rationale.

## Cross-Slice Coherence Review

Check the accepted views together:

- Does each workspace retain the hierarchy appropriate to its operator job?
- Do persistent objects, ownership, freshness, and authority project
  consistently without duplicating controls across the shell?
- Do shared components represent shared concepts rather than shared styling?
- Has equal material treatment flattened meaningful differences in priority or
  consequence?
- Do wide, compact, and phone views preserve intent rather than squeezing
  desktop controls into smaller space?
- Are state, focus, keyboard, and semantic-status rules coherent across the
  product?

## Acceptance Criteria

Phase 0.5 is complete only when:

- the user accepts the guide as Phase 1's visual implementation authority;
- every reusable pattern has a product role, state variants, accessibility
  behavior, and responsive treatment;
- semantic status is understandable without color alone and consequential
  controls have named keyboard paths and visible focus;
- the guide makes generic/unrelated-product drift recognizable;
- the guide and accepted references form one coherent product; and
- any remaining question is explicitly deferred because it cannot materially
  change the first Local Web Foundation slice.
